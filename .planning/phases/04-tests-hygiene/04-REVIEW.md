# Phase 04: Code Review Report

**Reviewed:** 2026-05-20
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

Five source files reviewed: the new admin conversations dashboard, the availability API proxy, the booking-flow test suite, and the test tooling config. `CLAUDE.md` was read for project context but is excluded from findings (documentation, not source).

The availability route and booking-flow tests are largely sound. The most serious findings are in the admin route: unhandled database exceptions will crash to an unformatted 500 with no security headers, and a global `LIMIT 100` on message retrieval silently truncates conversations across all pages rather than per-conversation. A secondary security gap is the lack of rate limiting on the public `/api/availability` endpoint, which is the only API route in this codebase that omits it. The test suite has two reliability issues around the `vi.resetModules` / `vi.doMock` pattern used in the `not_configured` test.

## Critical Issues

### CR-01: Unhandled database exceptions crash admin route without security headers

**File:** `app/admin/conversations/route.ts:185-236`

**Issue:** `renderDashboard` makes three `await sql\`...\`` calls with no try/catch. If any query fails (network hiccup, DB restart, schema mismatch), the uncaught rejection bubbles past the `GET` handler and Next.js returns a generic 500 response. That 500 response is generated by the framework, not by this handler, so **none of the `SECURITY_HEADERS` are applied** — the `X-Robots-Tag: noindex`, `Cache-Control: no-store`, `frame-ancestors 'none'`, and `WWW-Authenticate` challenge are all absent on the error response. The error page is technically an unauthenticated response that could be indexed or framed.

**Fix:**
```typescript
export async function GET(request: Request) {
  const authed = await verifyAdminBasicAuth(new NextRequest(request));
  if (!authed) {
    return new Response('Authentication required', {
      status: 401,
      headers: {
        ...SECURITY_HEADERS,
        'WWW-Authenticate': 'Basic realm="admin", charset="UTF-8"',
      },
    });
  }
  try {
    return await renderDashboard(request);
  } catch (err) {
    console.error('[admin/conversations] DB error:', err);
    return new Response('Internal Server Error', {
      status: 500,
      headers: SECURITY_HEADERS,
    });
  }
}
```

### CR-02: Global `LIMIT 100` on messages silently truncates per-conversation data

**File:** `app/admin/conversations/route.ts:219`

**Issue:** The query that fetches messages for the current page of conversations applies `LIMIT 100` globally across **all** conversations returned on the page (up to 20 by default). If page 1 contains even one high-volume conversation with 80+ messages, later conversations on the same page will have their messages silently cut off or absent. The dashboard renders `0 messages` or a truncated history for those conversations with no indication that data was omitted. An admin investigating a conversation could be misled into thinking a session was short when it was not.

**Fix:** Either remove the global limit and rely on the per-page conversation cap (max 20 conversations × reasonable depth), or add a per-`conversation_id` limit using `ROW_NUMBER()`:

```sql
SELECT id, conversation_id, role, content, token_usage, tool_calls::text, created_at::text
  FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY conversation_id ORDER BY created_at ASC) AS rn
    FROM messages
    WHERE conversation_id = ANY(${conversationIds}::uuid[])
  ) ranked
  WHERE rn <= 50
  ORDER BY conversation_id, created_at ASC
```

This caps each conversation at 50 messages independently rather than sharing a single pool.

## Warnings

### WR-01: `/api/availability` is the only public API route without rate limiting

**File:** `app/api/availability/route.ts:25-96`

**Issue:** Every other public API route in this codebase (`/api/book`, `/api/payment-intent`, `/api/chat`, `/api/widget-errors`, `/api/partial-booking`) applies rate limiting via `checkChatRateLimit` or `isRateLimited`. The availability endpoint is exposed without any throttle. A caller can hammer it in a tight loop, incurring Cal.com API calls on each request. Cal.com's own rate limits will eventually respond, but by then the upstream quota may be consumed, causing legitimate users to see 502 errors. The endpoint is fully public (no auth required).

**Fix:** Add an IP-based rate limit consistent with the pattern used in `/api/book`:
```typescript
import { getClientIp } from '@/lib/rate-limit';
import { checkChatRateLimit } from '@/lib/rate-limit-chat';

// Near the top of GET(), after param validation:
const ip = getClientIp(req) ?? 'unknown';
const rl = await checkChatRateLimit('ip', ip, { max: 30, windowSec: 60 });
if (!rl.allowed) {
  return NextResponse.json(
    { error: 'Too many requests' },
    { status: 429, headers: { 'Retry-After': String(rl.retryAfter ?? 60) } }
  );
}
```

### WR-02: Network failure on Cal.com fetch is unhandled — will throw 500

**File:** `app/api/availability/route.ts:67-73`

**Issue:** The `fetch()` call to Cal.com is not wrapped in a try/catch. A DNS failure, TCP timeout, or any network-level error will throw synchronously from `await fetch(...)`, producing an unhandled rejection that Next.js converts to a 500 with no `Cache-Control` or structured error body. The HTTP error path (lines 75-82) is correctly handled, but the network error path is not.

**Fix:**
```typescript
let slotsRes: Response;
try {
  slotsRes = await fetch(`${CAL_V2_BASE}/slots?${params}`, {
    headers: { ... },
    next: { revalidate: 60 },
  });
} catch (err) {
  console.error('Cal.com fetch failed (network):', err);
  return NextResponse.json(
    { error: 'Failed to reach availability service' },
    { status: 502 }
  );
}
```

### WR-03: `vi.resetModules` + `vi.doMock` in the `not_configured` test does not reliably affect already-imported modules

**File:** `lib/booking-flow.test.ts:149-185`

**Issue:** The `not_configured` test calls `vi.resetModules()` then `vi.doMock('./stripe', ...)` and dynamically re-imports `./booking-flow`. This pattern has a known reliability problem in Vitest: `vi.doMock` registered after `vi.resetModules` is not hoisted, so whether the dynamic `import('./booking-flow')` resolves with the new null-stripe mock depends on module graph traversal order and caching behaviour. In practice, the test may pass in isolation but fail when run as part of the full suite if the module registry is not fully cleared. The second `vi.resetModules()` at line 171 (inside the same test, after assertions) also leaves the module registry in an inconsistent state for subsequent tests in the same `describe` block; the top-level `vi.mock('./stripe', ...)` factory from lines 8-22 is not automatically re-applied after `resetModules`.

**Fix:** Use a module factory with a mutable reference instead of `resetModules`:
```typescript
// Top-level, hoisted
let stripeInstance: object | null = { paymentIntents: { update: vi.fn().mockResolvedValue({}) } };
vi.mock('./stripe', () => ({
  get stripe() { return stripeInstance; },
  toRef: (id: string, serviceId: 'review' | 'discovery') => { ... },
}));

// In the not_configured test:
it('not_configured — throws when stripe is null', async () => {
  stripeInstance = null;
  await expect(reconcileBookingFromIntent(makeSucceededPI())).rejects.toMatchObject({
    name: 'ReconcileError',
    code: 'not_configured',
  });
  stripeInstance = { paymentIntents: { update: vi.fn().mockResolvedValue({}) } };
});
```
This is idiomatic Vitest and avoids all `resetModules` sequencing hazards.

### WR-04: `escapeHtml` does not escape single quotes — breaks HTML attributes if output is ever moved into attribute context

**File:** `app/admin/conversations/route.ts:58-64`

**Issue:** The `escapeHtml` function escapes `&`, `<`, `>`, and `"` but not `'` (single quote → `&#39;`). Currently `escapeHtml` output is only injected into text node positions and double-quoted attribute values, so there is no active XSS vector today. However, `c.page_url` (line 104) is rendered in a `<td>` text node context — if that rendering were ever changed to embed the URL in a `href` attribute using single-quote delimiters, a visitor URL containing `'` could break attribute parsing. The omission is a latent risk that will silently surface when the template is extended.

**Fix:**
```typescript
function escapeHtml(text: string): string {
  return text
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#39;');
}
```

## Info

### IN-01: `message_count` from DB is rendered without escaping

**File:** `app/admin/conversations/route.ts:105`

**Issue:** `c.message_count` is the result of `COUNT(m.id)::text` cast in SQL — it will always be a numeric string like `"42"`. It is inserted directly into HTML at line 105 without going through `escapeHtml`. This is not a current vulnerability since PostgreSQL's `COUNT()::text` never returns arbitrary user data. It is however an inconsistency: all other DB-sourced strings go through `escapeHtml`, making this a code smell and a trap if the column definition changes later.

**Fix:**
```typescript
<td>${escapeHtml(c.message_count)}</td>
```

### IN-02: `vitest` and `@vitest/coverage-v8` should be in `devDependencies` — they are, but `vitest.config.ts` has no coverage config

**File:** `vitest.config.ts:1-9` / `package.json:47-48`

**Issue:** `@vitest/coverage-v8` is installed but `vitest.config.ts` contains no `coverage` block. Running `vitest run --coverage` would work but with default coverage settings (no thresholds, default reporter, no include/exclude). There is no `test:coverage` script in `package.json`. The package is paying the install cost for a capability that is never exercised.

**Fix:** Either add a `coverage` config block with meaningful thresholds, or remove `@vitest/coverage-v8` from `devDependencies` until coverage reporting is adopted:
```typescript
// vitest.config.ts
export default defineConfig({
  test: {
    include: ['lib/**/*.test.ts'],
    exclude: ['node_modules', 'app/**', 'widget/**'],
    environment: 'node',
    coverage: {
      provider: 'v8',
      include: ['lib/**/*.ts'],
      exclude: ['lib/**/*.test.ts'],
      thresholds: { lines: 80 },
    },
  },
});
```
